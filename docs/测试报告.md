## 6. 未覆盖 / 已知风险

- **镜像构建**：本环境无法访问 Docker Hub，`Dockerfile` 未实际构建。首次部署请执行 `docker compose up -d --build` 并按运维手册 §3 做日常检查。
- **真实交易所只读接口**：签名、权限判定、分页逻辑用 `httpx.MockTransport` 按官方响应格式测试；未用真实账户联调。
- **策略子进程断网**：在 root + Linux 下验证；容器内需 `SYS_ADMIN`，Windows 不支持（界面如实显示）。
- **72 小时网络判定**：逻辑用构造的时间序列测试；真实判定需部署满 72 小时。
- **前端**：没有自动化单元测试，依靠 TypeScript 类型检查与浏览器走查；端到端测试见下节（T12 已落地）。
- **PostgreSQL 路径未在本机实跑**：本机无 psycopg、无 Docker，故 `backend-postgres` 与 E2E 的
  `postgres` 腿只在 CI 跑。新增迁移的 PG 方言由 `db.py::_dialect_sql` 生成，本机只做了
  两种方言的生成核对（`?`→`%s`、`DECIMAL_T`→`NUMERIC(38,18)`、`AUTOINC_PK`→`BIGSERIAL`），
  **没有在真 PG 上执行过**。
- **Parquet 分支未在本机实跑**：`pyarrow` 未安装（它是可选 extra `parquet`），
  T06 的结果存储走的是 JSONL 回退路径；真实 Parquet 分支与 `S3ResultBackend` 只有接口与
  单元测试覆盖，没有对真实对象存储联调。
- **numpy 是核心依赖**：`pyproject.toml` 的 `dependencies` 里已声明 `numpy>=1.26`
  （因子研究用）。若本地环境未装 numpy，`tests/test_factor_research.py` 会在**收集阶段**
  报 `ModuleNotFoundError` 并中断整个 pytest 运行（不是跳过）。装依赖时请用
  `pip install -e ".[dev]"` 而不是逐个手装，以免漏掉。

设计要点：

- **单端口交付**：后端在 `web/dist` 存在时把前端构建产物当静态站点服务，
  所以 E2E 只起一个 HTTP 进程（无 Vite dev server、无代理、无跨域）。
- **独立 worker 进程**：`QAGENT_WORKER=external`，webServer 起 `qagent serve` 与
  `qagent worker` 两个进程，共享数据目录，走真实的租约/认领/检查点路径。
  `assertRanOnExternalWorker()` 用三层证据证明任务**不是**在请求线程里跑完的：
  `worker_mode === 'external'`、`/api/runs/workers` 有 60 秒内在线心跳、
  该 run 的 `state` 事件里 RUNNING 的 owner 不是 `inline:*`。
- **端口**：默认 8199，可用 `QAGENT_E2E_PORT` 覆盖；刻意避开 8000。
- **数据隔离**：`QAGENT_HOME` 指向 `tests/e2e/.tmp/home-<运行编号>`，每次运行路径都不同，
  既不落到开发者本机 `~/.quant_agent`，也不可能读到上一次运行的残留。
- **工作区隔离**：平台的注册契约是“受控注册”（bootstrap 后必须凭邀请码，且邀请码是
  **加入**已有工作区而非新建）。所以 E2E 统一先自注册部署管理员，再对每个 spec
  `POST /api/workspaces` 建一个**独立工作区**，各 spec 的策略、版本号、并发配额互不干扰。
- **本地逃生口**：Playwright 自带的 chromium 需从 CDN 下载。本机 CDN 实际拉不动
  （见 7.4），因此支持 `QAGENT_E2E_BROWSER_CHANNEL=msedge` 借用系统 Edge，
  以及 `QAGENT_E2E_VIDEO=off` 在没有 ffmpeg 时跳过硬录像。**CI 不设这两个变量**，
  走标准 chromium。

### 7.4 本机实跑结果

**E2E 在本机真实跑过，31 条全部通过（连续 3 次）。**

```
$ QAGENT_E2E_PORT=8799 QAGENT_E2E_BROWSER_CHANNEL=msedge QAGENT_E2E_VIDEO=off \
    npx playwright test --project=chromium

  31 passed (9.9m)
```

31 条 = 接口用例 23 条 + 浏览器用例 8 条（其中 2 条属 T05 的断线重连用例 `07`）。
配置用**仓库根的 `playwright.config.ts`**（不是临时配置文件），两个逃生口
`QAGENT_E2E_BROWSER_CHANNEL` / `QAGENT_E2E_VIDEO` 是 `web/playwright.config.ts` 里
正式支持的开关，CI 不设它们，走默认 chromium 与录像。

**浏览器来源（如实说明）**：Playwright 自带的 chromium **未能安装**。
两次 `npx playwright install chromium` 均卡住不返回，`%LOCALAPPDATA%\ms-playwright`
在 25 分钟内保持 0 字节落盘（只有 `.links` 与 `__dirlock` 两个空目录）；
网络本身通（`registry.npmjs.org` 可访问），但 Playwright 的 CDN 在这台机器上拉不动。
因此浏览器用例改用**系统已安装的 Microsoft Edge 155**（`channel: 'msedge'`）执行。
Edge 与 chromium 同源，这批断言（角色/文案/表格/文件选择器/confirm 对话框）与浏览器品牌无关，
但**严格来说本机的浏览器用例是在 Edge 上验证的，不是在 Playwright 自带 chromium 上**。
CI 上会用 `npx playwright install --with-deps chromium` 装标准 chromium，不受此限制。
另外本机缺少 ffmpeg，`video: 'retain-on-failure'` 会让每条浏览器用例在 `newPage` 就失败，
故本地以 `QAGENT_E2E_VIDEO=off` 运行（截图与 trace 仍在）。

### 7.6 缺陷发现与修复

E2E 与全量测试期间发现并确认了以下问题。**每一项都已修复并验证**（验证方式逐条写在下面）：

1. **JSON 视图写入不完整规则后切回表单白屏（已修）**
   `web/src/pages/DslEditor.tsx` 对结构不完整的 spec 执行 `Object.entries(undefined)`
   抛 TypeError，React 卸载整棵树导致整页白屏。属 T04 引入的回归（T04 当时未做浏览器验证）。
   - 修法：渲染时先做一层 `form` 默认值兜底（`timeframe`/`params`/`indicators`/`entry`/
     `position`/`risk`），表单的**读**走 `form`，**写**仍以 `spec` 为准，服务端校验契约不变。
   - 验证：`02-dsl-backtest.spec.ts` 4/4 通过；另用一条临时复现 spec 确认白屏消失
     （修复前 `pageerror: Cannot convert undefined or null to object`、`select 数量 = 0`；
     修复后 `select 数量 = 9`、标题仍在）。

2. **`JsonStore` 读写竞争导致 `os.replace` 偶发 `WinError 5`（已修）**
   - 现象：`POST /api/dsl/strategies` 偶发 500；`roles.json` 的原子替换报
     `PermissionError: [WinError 5] 拒绝访问`。E2E 全量跑时复现到一次。
   - 根因：**写**路径拿跨进程文件锁（`upsert`/`delete` → `with self._lock, self._xlock(...)`），
     而**读**路径（`list()` / `get()` → `_load()`）只拿线程锁。于是进程 A 正 `read_text()`
     打开 `roles.json` 时，进程 B 执行 `tmp.replace(path)` 就会因目标被占用而失败。
     API 与 worker 是两个进程、worker 启动即写角色，所以真实部署也会撞。
   - 对照实验（真实多进程，7 秒）：读者裸 `read_text()` → 读者共报错 **28 次**
     （17 + 11）；修复后同样实验 **0 次**。
   - 修法（`src/quant_agent/store/__init__.py`）：
     a) `_load()` 读盘时也进 `_xlock`（缓存命中不碰文件，仍是快路径；进锁后重新取签名，
        避免把等锁期间已被替换的旧内容写回缓存）；
     b) `_flush()` 的 `replace` 加**有界重试**（`_REPLACE_RETRIES = 10`，递增退避），
        重试耗尽仍照常抛出，不吞异常；
     c) `_FileLock` 支持**同线程重入**——否则 `upsert` 持锁后再调 `_load` 会自己等自己
        （Windows 的 `msvcrt.locking(LK_LOCK)` 对同一区间重复加锁会阻塞）。用
        `threading.local` 记重入层数，保证按线程判定。
   - 回归测试：`tests/test_store_locking.py`（5 条），其中并发那条用**独立子进程**才有效
     （同进程线程会被 `RLock` 串行化，掩盖竞争）。已验证其确实能抓到缺陷：
     还原 `_load` 后该用例报 **221 次** `PermissionError`；去掉重入分支后
     `upsert` 直接**死锁**（用例超时）。

3. **策略隔离子进程收尾时的 `OSError: [Errno 22]` 噪声（已修）**
   - 现象：全量测试出现 `PytestUnraisableExceptionWarning`，来自 `api/tasks.py` 的后台回测线程，
     栈底在 `platform/isolation.py`。加 `-W error::pytest.PytestUnraisableExceptionWarning`
     跑全量会变成 1 failed。
   - 根因：`_Child.close()` 只送 `exit` 并 `wait`，**从不关闭 stdin/stdout/stderr**。
     于是 `_drain_err` 那个 daemon 线程一直阻塞在 `for line in self.proc.stderr`，
     直到解释器退出时才对**已被 finalize 的句柄**做一次读。
   - 修法：`close()` 显式按序收尾——先关 stdin（让子进程读到 EOF 自行退出）→ `wait` →
     关 stdout/stderr → 必要时 kill → 清理工作目录；并让 `_drain_err` 捕获
     关闭时的 `ValueError`/`OSError` 安静退出。
   - 验证：`pytest -q -W error::pytest.PytestUnraisableExceptionWarning` → **743 passed**
     （修复前为 1 failed / 742 passed）。

4. **E2E 自身的三处时序/选择器缺陷（已修，属测试侧而非产品）**
   - `04-paper` 在 run 已 `RUNNING` 后立刻断言**会话** `status`：会话状态由 worker 步进时写入，
     比 run 的 state 晚一拍，实测出现 `running` vs `queued` 的瞬时差。加
     `waitPaperSessionStatus()` 等它变到位。
   - `helpers.uiStartPaper` 用 `getByRole('heading', { name: '模拟交易' })`：`Panel` 的
     `subtitle` 会写进 `panel-info` 的 `aria-label`，使「启动新实验」那个面板的
     可访问名含「模拟交易」，子串匹配命中 2 个元素而报 `strict mode violation`。
     改用 `exact: true, level: 1` 锁定页面标题（`02`/`06` 同类断言一并加固）。
   - `07-ws-reconnect` 的两处断言错误：①「断网期间页面不应有新事件」原本在
     `setOffline(false)` **之后**才读页面，测的其实是"恢复后补齐还没发生"，属异步竞态；
     改为**仍在离线时**读。② 与后端比对时要求页面序列等于"断网后新增序列"，
     等于要求面板**丢掉历史**，与紧邻的第 13 步（要求保留断网前那一段）自相矛盾；
     改为断言"新增段是页面序列的尾部，且剩余前缀与断网前逐项一致"。
     修完后 `07` 2/2，且连跑 3 次稳定。

5. **API 语义确认（非缺陷，供文档补充）**：`DELETE /api/imports/{id}` 是**软删除** ——
   它清掉该次导入的成交/流水/快照并把 `imports.status` 置为 `deleted`，行本身保留供审计。
   因此 `GET /api/imports` 仍返回该行，界面靠 `status === 'done'` 过滤
   （`web/src/pages/Live.tsx`）。E2E 已按此语义断言（状态变 `deleted`、明细清空、`live_fills` 归零）。
   `docs/API参考.md` 目前只写“删除一次导入及其数据”，建议补充“软删除 + 记录保留”。

6. **口径确认（非缺陷）**：`AttributionReport.summary()` 的 `live_fills` 是
   **真实成交总笔数**（已归因 + 未归因），与归因**行数** `attributed` 不是同一口径。
   E2E 按 `live_fills === attributed + unattributed` 断言。

7. **另修一处真实前端缺陷（已修）**：`web/src/pages/Live.tsx` 在 `liveStatus()` 失败时
   只 `notify` 一下就返回，`status` 永远为 `null`，配合 `if (!status) return <Loading />`
   变成**永久转圈**——用户既看不到错误也没有重试入口。改为把失败记进 state，
   显示「加载失败 + 重试」。这正是 `06-live-comparison` 浏览器用例曾经卡在「加载中…」的原因。

8. **T07 的用量面板此前没有接到界面上（已补）**：后端 `GET /api/workspace/usage`
   （`platform/quota.py::panel`）一直在返回「已用 / 上限 / 剩余 / 占比」，
   但前端从未调用过它 —— T07 卡片要求的「设置与审计 → 工作区显示用量与上限」
   实际上没落地。已在 `web/src/pages/Settings.tsx` 的「工作区与额度」页加入用量面板：
   7 个计量项（回测 CPU 秒、回测次数、优化组合数、LLM 调用次数、LLM token、数据下载量、
   存储占用）逐行显示已用/上限/占比，已耗尽的标红并打「已耗尽」标签。
   数值全部用后端给的十进制字符串，**占比也在后端算**（浮点会把 99.9% 显示成 100%，
   看起来像已耗尽）；字节类只做显示层换算并保留原始字节数。
   已用真实浏览器验证：面板渲染出 7 行、`回测 CPU 秒 0 秒 / 3600 / 0% 当日`。

9. **T08 的「拆单」在界面上不可见（已补）**：`attribution.summary()` 一直在返回
   `merged_orders`（多少个订单被交易所拆成多笔成交后归并成一行）与每行的 `live.fills`，
   但 `Live.tsx` 只显示滑点与置信度，用户看到「真实成交 3 笔 / 报告 1 行」会以为丢了成交。
   已在对照报告里增加「被拆单的订单 N 个」指标卡（>0 时才出现），
   并在明细行标出「· 3 笔合并」。

10. **T11 的双因素只有后端、界面完全没有（已补）**：`/api/auth/totp*` 五个端点与
    `login(totp_code=...)` 都在，但 `web/` 里搜不到任何 `totp` 字样 ——
    T11 卡片要求的「用户可在设置 → 账号启用 TOTP」与「登录时补验证码」
    在界面上都不存在，用户启用不了、启用了也进不去。已补：
    - `web/src/pages/Login.tsx`：登录返回 401 + `details.totp_required` 时**不报错**，
      而是切到「两步验证」第二步，复用同一端点带上验证码重发；
      另给「换一个账号」的退路。
    - `web/src/pages/Settings.tsx` 的「我的账号」页加入双因素区块：
      开始启用（显示 otpauth 链接与密钥，**此时尚未启用**）→ 输入一次真实验证码确认 →

      （少了任何一个，拿到一台未锁屏的浏览器就能关掉 2FA）。

    - 真实验证（**不 mock**，用独立实现的 RFC 6238 算法算验证码）：
      密钥 32 字符、`otpauth://totp/QuantLab%3A…?secret=…&algorithm=SHA1&digits=6&period=30`；
      错误验证码 → 401 `UNAUTHENTICATED`；正确验证码 → 200 + **10 个**恢复码；
      不带验证码登录 → 401 且 `details.totp_required=true`；
      浏览器里切到「两步验证」→ 输入验证码 → 进入工作台；
      恢复码可登录（200）、**同一恢复码第二次使用被拒**（401，防重放）；
      状态接口不回显密钥与恢复码。
