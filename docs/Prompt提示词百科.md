## 1. 什么是提示词

提示词（Prompt）就是你交给大模型的**指令 + 上下文 + 期望输出**。它不是"咒语"，而更接近你在给一位**聪明但不了解你项目背景的新同事**写工作说明。写得越具体、边界越清楚，产出越可用。

在本平台里，你的提示词会被 Agent 自动套进一个"系统提示"（角色、SDK 文档、平台约束），所以你**不用**从头描述平台是什么——你只需要描述**你的策略意图**。

---

## 2. 提示词的六个基本元素

一个高质量的量化提示词通常包含这六块。缺哪块，大模型就会"自由发挥"哪块（通常是坏事）。

| 元素 | 作用 | 例子 |
| --- | --- | --- |
| 角色 | 让它以什么身份工作 | "你是一名现货量化研究员" |
| 任务 | 要做什么 | "生成一个均线突破策略" |
| 上下文 | 相关背景数据 | "标的 BTCUSDT，1 小时周期" |
| 约束 | 不能越界的红线 | "只输出目标仓位，不调用交易所" |
| 输出格式 | 要什么形状的结果 | "输出 Python 代码 + 参数表 + 风险说明" |
| 示例 | 给它参照 | 附一个已有策略作为范式 |

**一句话记忆：角色 + 任务 + 上下文 + 约束 + 格式 + 示例。**

## 3. 结构化写法

### 3.1 用分隔符把"指令"和"数据"分开

大模型容易把数据和指令混淆。用清晰分隔能显著降低出错率。

```
请审查下面这个策略的过拟合风险。

<strategy_code>
{{这里粘贴策略代码}}
</strategy_code>

<backtest_metrics>
{{这里粘贴回测指标}}
</backtest_metrics>

要求：只分析过拟合，不要改写代码。
```

### 3.2 XML 标签 / Markdown 标题

- **XML 标签**：`<task>...</task>`——适合机器解析，平台模板多用它。
- **Markdown 标题**：`## 任务`——适合人阅读，适合长文。

两者可混用。关键是**一致**：同一份提示词里别有时用 `<task>` 有时用 `## 任务`。

### 3.3 变量占位符

平台提示词模板用 `{{变量名}}` 占位，运行前自动填充：

| 变量 | 含义 |
| --- | --- |
| `{{symbol}}` | 交易标的，如 `BTCUSDT` |
| `{{timeframe}}` | 周期，如 `1h` |
| `{{strategy_name}}` | 策略名 |
| `{{strategy_code}}` | 策略代码 |
| `{{metrics}}` | 回测/模拟指标 JSON |
| `{{constraints}}` | 风控约束 |
| `{{user_input}}` | 用户原始输入 |

### 3.4 用示例（few-shot）锁定风格

与其用一百字描述"我想要什么样的代码"，不如给一个**短示例**：

```
请按下面的风格生成策略（这是一个示例，不要照抄逻辑）：

```python
class Strategy:
    def initialize(self, ctx):
        self.fast = 10
        self.slow = 30
    def on_bar(self, bar):
        if bar.fast_ma > bar.slow_ma:
            ctx.set_target_position(1.0)
        else:
            ctx.set_target_position(0.0)
```
```

## 4. 量化场景模板库

以下模板已内置到平台 `prompts/` 目录，Agent 通过 `prompt_id` 自动引用。你可以直接复制改造。

### 4.1 策略生成

```
<TASK>根据用户描述生成一个可回测的策略。</TASK>

<CONTEXT>
标的：{{symbol}}
周期：{{timeframe}}
用户的策略想法：{{user_input}}
平台策略 SDK 契约见系统提示。
</CONTEXT>

<CONSTRAINTS>
1. 只输出目标仓位（ctx.set_target_position），禁止调用交易所或网络。
2. 必须使用已收盘的 bar，禁止使用未来数据。
3. 必须包含止损与仓位上限。
4. 若用户描述缺少关键参数，先列出需要澄清的问题，不要臆测。
</CONSTRAINTS>

<OUTPUT_FORMAT>
A. 策略逻辑说明（3–5 句）
B. Python 代码（实现 initialize / on_bar / snapshot / restore）
C. 参数表（名称、默认值、范围、含义）
D. 风险与局限（成本敏感、震荡失效等）
</OUTPUT_FORMAT>
```

### 4.2 策略审查

```
<TASK>审查以下策略，指出主要风险，不改写代码。</TASK>

<STRATEGY_CODE>{{strategy_code}}</STRATEGY_CODE>
<METRICS>{{metrics}}</METRICS>

<CHECKLIST>
- 是否使用了未来数据（look-ahead）？
- 是否只在盈利交易上扣费？
- 回撤控制是否只有仓位上限、没有止损？
- 参数是否过拟合（在样本外是否崩掉）？
- 是否把"价格触及"当成"全部成交"？
</CHECKLIST>

<OUTPUT_FORMAT>逐条结论 + 总体评级（低/中/高风险）+ 建议的验证实验。</OUTPUT_FORMAT>
```

### 4.3 调研任务

```
<TASK>调研指定策略/标的市场表现的背景信息。</TASK>
<CONTEXT>标的：{{symbol}}；策略类型：{{strategy_name}}；关注区间：{{timeframe}}</CONTEXT>
<CONSTRAINTS>
- 区分"事实"与"推测"，推测需标注。
- 不得给出投资建议或收益承诺。
- 引用平台历史实验数据（query_runs）时注明 run_id。
</CONSTRAINTS>
<OUTPUT_FORMAT>要点式摘要（≤300 字） + 数据来源 + 未解决问题。</OUTPUT_FORMAT>
```

### 4.4 回测解读

```
<TASK>把回测指标翻译成人话，并指出可信度。</TASK>
<METRICS>{{metrics}}</METRICS>
<CONSTRAINTS>短区间年化可能夸大结果，需同时引用实际收益、交易次数、观测天数。</CONSTRAINTS>
<OUTPUT_FORMAT>
1. 一句话结论
2. 收益/风险/交易/执行四个维度各一段
3. 可信度评估（样本量、样本外、压力测试）
4. 下一步建议实验
</OUTPUT_FORMAT>
```

### 4.5 风控校验

```
<TASK>检查策略是否符合账户与策略层风控。</TASK>
<CONSTRAINTS>{{constraints}}</CONSTRAINTS>
<STRATEGY_CONFIG>{{strategy_config}}</STRATEGY_CONFIG>
<OUTPUT_FORMAT>违规项列表 + 每条对应的调整建议。合规则明确回复"通过"。</OUTPUT_FORMAT>
```

### 4.6 复盘 / 长期 Agent 摘要

```
<TASK>生成一份截至 {{date}} 的策略简报。</TASK>
<DATA>{{daily_digest_data}}</DATA>
<CONSTRAINTS>
- 不超过 200 字，适合微信阅读。
- 只陈述数据，不预测未来。
- 若存在异常（订单 UNKNOWN、对账差异、任务失败），必须在开头提示。
- 结尾固定附："仅为研究结果，非投资建议。"
</CONSTRAINTS>
<OUTPUT_FORMAT>标题 + 3–5 行要点 + 免责声明。</OUTPUT_FORMAT>
```

### 4.7 通知摘要（微信推送）

```
【策略简报】{{date}}
· 净值：{{nav}}（{{period}}：{{change}}）
· 最大回撤：{{mdd}}
· 交易：{{trades}} 笔，胜率 {{win_rate}}
· 异常：{{alerts}}
仅为研究结果，非投资建议。
```

### 4.8 角色提示词（团队调研用）

角色提示词和上面这些"任务模板"不一样：任务模板描述**要做什么**，角色提示词描述**以什么身份、带什么偏见、必须检查什么**。

一条好的角色提示词包含四块：

```
你是<身份>，服务于一个量化研究团队。

【职责】
1. …
2. …

【必须检查的清单】
- …
- …

【硬性约束】
- 必须具体，禁止空话（如"市场有风险"）
- 无法判断时明确说明缺少哪项信息

【输出格式】
①… ②… ③…
```

平台内置 9 个预设角色，它们的提示词就是按这个结构写的：

| 角色 | 它的"偏见"是什么 |
| --- | --- |
| 市场分析师 | 只说数据支持的结论，推测必须标注 `[推测]`；数据不足就说数据不足 |
| 策略设计师 | 先逼你说清"这个策略赚谁的钱、在什么条件下成立"，再谈参数 |
| 量化工程师 | 输出代码后必须列出"这段代码可能出错的地方" |
| 回测分析师 | 职责不是报喜，是判断结论可不可信；必须给出低/中/高评级 |
| 风控官 | 默认立场是"先假设这个策略会出事"；给的是必须修正项，不是泛泛建议 |
| 反方质疑者 | 职责是攻击不是附和；必须构造具体反例，禁止空话 |
| 合规官 | 只挑表述问题，逐条给出"原文 → 改写" |
| 执行与成本专家 | 必须区分保守/基准/乐观三档；不得把价格触及当成全部成交 |
| 研究组长 | 不得假装分歧不存在；不得因历史收益高就放行 |

**写角色提示词的两个常见错误**：

一是把任务写进角色。"你是风控官，请检查这个策略"——后半句是任务，应该由运行时传入。
角色提示词只该定义**身份与检查清单**，具体任务由调用方给。

二是角色之间职责重叠。三个角色都在做"风险评估"，产出就会重复且互相稀释。
让每个角色有**独特的偏见**，团队才有价值：有人负责找机会，有人负责找漏洞，有人负责找表述问题。

**用 AI 起草角色**：在「角色库」页面用一句话描述你想要的角色，平台会产出一张完整角色卡
（名称、定位、系统提示词、温度、工具、输出格式、标签），你确认后入库。如果模型不可用，
平台会退回一张模板角色卡，不会报错。

### 4.9 团队调研的编排提示词

团队运行时会自动给每个角色前置一段"共同红线"，你不用在角色提示词里重复写：

```
【团队共同红线】禁止调用交易所、网络或任何下单接口；禁止使用未来数据；
不得给出投资建议或收益承诺；区分事实与推测；不确定时明确说明。
```

流水线模式下，后一个角色会看到前面所有角色的产出；对抗模式下，质疑角色会拿到其他角色的观点
并要求"指出最脆弱的假设、构造具体反例、指出哪些结论看起来像证据其实不是"。

## 5. 反模式与排错

| 反模式 | 后果 | 改法 |
| --- | --- | --- |
| "帮我写个能赚钱的策略" | 大模型会编出看似合理但无法验证的逻辑 | 给出标的、周期、逻辑假设、约束 |
| 一句话丢给模型，不设约束 | 可能生成调用交易所的代码 | 明确"只输出目标仓位" |
| 把未来数据当输入 | 回测虚高 | 在约束里写"只用已收盘 bar" |
| 要求"高收益低风险" | 得到无法实现的承诺 | 要求输出风险与局限 |
| 提示词里混入密钥 | 泄漏 | 密钥走环境变量/钥匙串 |
| 只让模型看最佳结果 | 强化过拟合 | 让它看全部参数尝试 |
| 对话无限拉长不压缩 | 上下文爆炸、成本飙升 | 用平台上下文管理器自动压缩 |

**排错三步**：① 补约束；② 给示例；③ 拆任务（一次只让它做一件事）。多数"模型不听话"其实是"指令不完整"。

## 6. 与平台集成

- 平台把上述模板存为 `prompts/*.md`，带版本号，实现**提示词版本化**。
- Agent 运行时按 `prompt_id` + `{{变量}}` 渲染，记录 `prompt_hash` 到 `StrategyVersion`，保证可复现。
- 你可以在 `~/.quant_agent/prompts/` 放**自定义模板**覆盖内置，随时迭代。
- 温度建议：代码生成 `0.0–0.3`（要确定性）；调研/报告 `0.3–0.7`（要表达力）。

## 7. 常见问题

**Q：提示词写得越详细越好吗？**
不是。细节要在"约束"和"格式"上，冗余的背景描述反而稀释重点。原则：**能约束的写死，不能确定的要求澄清**。

**Q：为什么 Agent 生成的代码不能直接上实盘？**
因为平台红线：LLM 只产出候选，必须经测试 → 版本审核 → 回测 → 样本外验证，且 `human_approved=true` 才进实时模拟。这是原方案"结果可追溯、策略只能生成信号"的纪律。

**Q：模型答非所问怎么办？**
先检查约束是否明确，再给一个示例，最后才考虑换模型。多数问题在提示词，不在模型。

**Q：多个 Agent 各自的提示词怎么管？**
每个 Agent 有独立 `prompt_id` 前缀（如 `strategy_gen.*`、`research.*`、`digest.*`），互不干扰，均可版本化。

**Q：能用国产模型吗？**
可以。平台 LLM 层支持 OpenAI 兼容接口，DeepSeek、通义、Kimi、本地 vLLM/Ollama 都能接入，配置见增补设计第 2 章。
