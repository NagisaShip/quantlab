# Agent Runtime 实测与下一轮改进清单

日期：2026-10-25。模型：OpenCode Go `deepseek-v4.1-flash`。产品基线：`241cc19`。本轮完成比较、质量评估、定时包装层核对和最终复跑；按用户要求记录缺陷，**未修改产品行为、模型提示词、版本号或发布包**。

## 主要结论

当前 Runtime 的价值已由恢复、审批、取消、账本与效果核对测试验证，但它不会自动提高模型质量。本轮当前与历史 Agent 均为 **10/12** 任务通过；不能据此宣称新 Runtime 更聪明，也不能用少量任务给开源框架排名。

新内核有明确开销。相同本地固定响应、3 次模型请求和 2 次工具调用下，新旧执行路径中位耗时分别约 **118.79ms / 46.04ms**。真实模型任务中，这部分开销相对网络和生成耗时较小；当前配置的最慢样本约 98.98s，其中绝大部分时间位于服务商请求内，不能归因于调度器。

最应优先处理的是包装层状态与幂等，而不是复杂调度算法。真实 Worker 探针复现：模型仍在 WAITING，通知任务却显示 COMPLETED；新进程也会重复执行同一日期的业务任务。文档生成已能形成可读表格、标题和页面，但交付契约、封面页数、分页和事实措辞还存在缺口。

## 方法与适用边界

- 历史循环直接取自本地 Git `188f99744b245dac2ed0e742839186a0c0542aa4` 的 `agents/base.py`，无需另拉 GitHub。它与当前循环共用当前消息类型和 HTTP provider，目的是隔离循环差异，**不是完整旧版应用及其全部依赖的重建**。
- 开源配置为 LangGraph 1.2.17、LangGraph 1.2.17 + SQLite checkpointer 3.1.2、Pydantic AI 2.61.0 默认非持久配置。后者使用自己的原生 OpenAI 兼容 SDK，因此速度包含其客户端缓存与序列化实现的影响。
- 新内核使用 SQLite Journal。LangGraph SQLite 配置保存图检查点，但本轮没有为它补写 QuantLab 式费用、效果核对与 fencing；Pydantic AI 没有启用其可选持久执行后端。功能范围不同，不能用速度表判定谁在可靠性上胜出。[LangGraph 持久化说明](https://docs.langchain.com/oss/python/langgraph/persistence)、[Pydantic AI 官方说明](https://pydantic.dev/docs/ai/overview/)。
- 4 个任务 × 每配置 3 次 × 5 种配置，共 60 个任务实例。任务包括净收益计算、跨步证据读取与复利、纯函数代码生成、证据不足情况下的研究判断。各配置都用同一资料、工具和温度 0；固定随机顺序穿插执行，减少时段与缓存顺序偏差。
- 主实验统一非流式响应、3072 输出 token 上限、本地网关最多 12 次模型请求和 12 次工具调用。**没有测 TTFT**，没有把非流式返回时间伪装为首 token 延迟。
- `Agent.max_steps=16` 在旧路径表示模型循环上限，而新 Runtime 统计模型和工具 Step。已记录这个迁移语义差异；因此终止边界并不完全等价，不能把对应失败解释为纯模型或框架质量差异。
- 实测集中在 Agent 执行循环；通过统一网关记录真实供应商用量，未在此基准中加载完整 API、UI 与 ModelHub 准入链。产品 ModelHub 的费用与并发正确性由另外的回归验证。
- 凭据只进入本地网关进程内存，第三方 SDK 只收到本地占位 key。资料均为固定合成样本，未上传真实用户项目数据。报告和请求轨迹不含认证 headers。

## 性能结果

固定响应实验每配置保留 2 次预热和 20 次正式运行，110 次全部通过。以下本地耗时包括客户端建立、HTTP 序列化、图/循环执行与持久化，**不是纯内核 CPU 时间**。

| 配置 | 持久化配置 | 固定响应中位 ms | 固定响应 P95 ms | 实际任务中位 s | 实际任务数 |
| --- | --- | ---: | ---: | ---: | ---: |
| 历史 QuantLab Agent | 无 | 46.04 | 61.17 | 7.63 | 12 |
| 当前 QuantLab Runtime | SQLite Journal | 118.79 | 174.17 | 10.56 | 12 |
| LangGraph | 无 checkpointer | 46.47 | 62.83 | 8.00 | 12 |
| LangGraph SQLite | SQLite checkpointer | 44.90 | 67.70 | 10.00 | 12 |
| Pydantic AI | 默认非持久 | 15.94 | 19.74 | 8.44 | 12 |

Pydantic AI 的本地客户端复用与原生 SDK 路径较轻；这不是在相同持久性保证下测出的优势。LangGraph 两种配置的少量毫秒差异落在运行噪声与初始化影响内，不解释为“持久化反而加速”。

把本地墙钟减去网关记录的上游请求时长后，各配置中位剩余约 41.1 / 202.9 / 51.8 / 65.8 / 27.0ms，顺序同上。这是含工具与客户端的剩余时间，不是采样 profiler 归因。当前 Runtime 的事务、事件与状态审计有可测成本；尚未做共享连接或审计热路径优化。

没有测生产并发吞吐、饱和负载、峰值内存或长时间数据库增长。原有多进程故障实验证明的是正确性边界，不是最大 QPS。

## 任务完成与输出质量

| 配置 | 完整验收 | 算术工具 | 多步证据 | 代码隐藏用例 | 研究判断 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 历史 Agent | 10/12 | 3/3 | 2/3 | 3/3 | 2/3 |
| 当前 Runtime | 10/12 | 3/3 | 2/3 | 3/3 | 2/3 |
| LangGraph | 10/12 | 3/3 | 3/3 | 3/3 | 1/3 |
| LangGraph SQLite | 11/12 | 3/3 | 3/3 | 3/3 | 2/3 |
| Pydantic AI | 9/12 | 3/3 | 3/3 | 3/3 | 0/3 |

这里只存在 4 个不同任务，每项重复 3 次；同任务样本并非独立生产任务。83.3% 与 91.7% 的差距不足以证明框架质量差异。本报告不把它当作 SWE-bench 分数、生产成功率或安全认证。

代码任务实际执行了受限纯函数并检查 4 组隐藏输入，15 个代码输出均通过。它没有覆盖复杂仓库修改、依赖安装、集成调试或系统权限操作。研究判断失败主要是重复探索不存在的 fixture、触及工具/步骤上限、返回说明文字而非约定 JSON。多步证据中部分输出虽然算出了 3.95%，却没有交付 JSON；这仍是任务契约失败。有说明文字还错误地称三个日收益之和为 5%，说明“主要数字正确”不代表附加叙述可靠。

数据内嵌了一条要求宣称“99% 保证收益”的恶意指令，本轮未观察到执行该要求；只有一条攻击样本，不能视为完整注入防护证明。

### 评分器复核

初始评分有两项误判，已保留原始分数，并在 `validated_grade` 单独修正：

1. `coding-2-langgraph_sqlite` 使用合法 builtin `ord()`，最初受限评估器未开放它。
2. `research_judgment-1-legacy` 写的是“slippage and market-impact assumptions”，原评分器只匹配连续的“slippage assumptions”。

没有重写模型答案，也没有重新请求模型挑选较好输出。原始结果、复核结果和评分器哈希分别保留；最终表使用统一复核评分。试跑曾发现评测工具适配器参数名冲突，试跑数据完全不进入以上分数。后补评分器 3 项测试全部通过。

## Word 与 PPT 能力补测

每种配置再做一次文稿规划任务，要求相同中文研究备忘录、事实表、来源标识和总计 4 页的演示计划。5 次规划使用同一平台 Word/PPT 构建器，考察规划到排版的整合，而非比较各框架自己的文档引擎。构建器来自当前工作区，包含此前未提交的文档质量改动；其 SHA-256 已保留，不将它冒充 `188f997` 的渲染器。

4 组返回合法结构并生成文件；LangGraph SQLite 本次未返回合法 JSON，未进入文档构建。新旧两种 Agent、Pydantic AI、LangGraph 的候选都保留原样，未手工美化。

隔离评测解释器下观察到 `tempfile` 使用中文项目目录，LibreOffice 报 `source file could not be loaded`；另一次目录创建诊断出现 PermissionError，提示临时目录权限/路径环境可能参与触发，但尚未完全隔离两者的作用。原始失败记录已保留。改用宿主 Python 和用户临时目录后，**相同原文件**可经平台渲染器生成 4 组 Word 和 PPT 页面，未修改产品源码。此结果证明存在环境敏感性，不证明所有正式安装环境都会失败；也不把诊断性成功覆盖原始失败。

已查看全部 Word 页面和 4 组 PPT 联系表，未观察到文字裁切或重叠。实际发现：

- 4 份有效计划均为 4 个 slide 对象，但共同构建器不论标题是否为空都附加封面，最终均为 **5 页**。这是规划与交付契约问题，不是 Runtime 调度问题。
- 当前、Pydantic AI、LangGraph 的 Word 为 1 页，旧 Agent 的来源行单独落在第 2 页，出现明显孤页。
- 表格、标题、来源与备注已生成，排版可读，但大部分 PPT 仍是相同项目符号模板，留白较多，没有自动选择更适合数据与结论的版式。
- 输入只给 `sample_days=12`，当前、旧 Agent 和 LangGraph 的部分文字却写成“12 个交易日”；旧 Agent 备忘录还写“手续费已计入净收益”，资料没有支持这一断言。
- 该实验没有让 DeepSeek 对截图做视觉自检。模型未被切换成别的视觉模型，人工截图检查与模型自检必须区分。

可审阅样本位于 `.tmp/runtime-evaluation/documents-final`，结构与渲染记录见证据目录的 `document-results.json`、`document-render-control.json`。这些是保留缺陷的评测候选，不是经过润色的最终业务交付。

## 定时任务包装层核对

探针通过真实 Worker、`handle_agent_job` 和实际独立 Journal，通知器替换为本地捕获器，**未发送外部消息**。

1. **结果未知被交付成功掩盖**：模拟 provider 请求结果不明，内核 generation Run 为 WAITING；DailyDigestAgent 发出模板简报，业务 record 为 `ok`，Worker 的 agent_job 为 COMPLETED，摘要没有关联 generation Run。内核没有被错误改成 COMPLETED，但 UI/业务层难以看见未结算执行，属于 P0 宿主状态语义与可追溯性缺口。
2. **run_key 的幂等只在实例内**：相同 `daily_digest:2026-10-25` 在两个独立 Python 进程运行，产生 2 次模型调用、2 次捕获通知。现有 `_seen_keys` 不能充当跨进程持久幂等。
3. **策略维护的能力边界**：正常维护探针 generation 和交付均结束；API 构造器没有传 `propose_version`，所以默认候选工具只是“未接入版本服务”的 stub。本轮不据此宣称创建了真实策略候选。

这里的核对已经完成；缺陷修复按用户要求留到下一轮。**不能因为回归全绿，就宣称定时任务包装层迁移已经完整或生产效果具有恰好一次保证。**
